# tusp-pddl-models

This repository was originally intended as a companion-piece to my MSc thesis on [Using PDDL models to solve TUSS](https://repository.tudelft.nl/record/uuid:242e8fdd-95d2-4915-bd28-f0697559514e). 


## Domains folder

This folder contains all domains used for experiments in the MSc thesis. As explained in the paper, models are split in four categories: 
1. Temporal & Numeric, Exact train locations
2. Temporal & Numeric, Relative train locations
3. Numeric, Exact train locations
4. Numeric, Relative train locations

Inside the folder for each category the *config.csv files explain what modelling decisions were made in the domains. This information is important, as it is necessary to determine the correct parameters in an instance generator. When the parameters in the instance generator do not match the description in the config, the generated PDDL problem file might not be compatible with the PDDL domain file.

## Generator folder

This folder contains code written for the instance generator. This class will create a PDDL problem file based on the provided input. 

### Instance generator

To model a planning problem in PDDL we need a domain file and a problem file. The domain file is not generated by code in this repo, but many are provided (I created these manually). The instance generator will generate problem files for **TUSS PDDL domains**. It is important to note that I have written these generators specifically based on the naming conventions I used in my domains, which describe the TUSS problem in varying levels of detail.

Based on the modelling decisions made in the domain files, different descriptions are needed in a corresponding problem file. To create a matching problem file you must provide the instance generator with:
- A description of a shunting yard layout (JSON format, examples provided)
- A description of a scenario (JSON format or created with a scenario generator)
- Correctly selected options for parameters describing modelling decisions (How cost is modelled, whether driver objects are included etc...)
- Names of domain and problem files


To describe a scenario you must provide:
- A list of incoming trains (in order). Every train is described by:
    - a name
    - a length
    - whether it exists in its current description at the start of the problem (available=true/false)
- A list of outgoing trains (in order). 

This can be done in JSON format.

Something interesting is also the __visualize()__ method that can be called on a ShuntingYard instance. This plots the shunting yard layout as a graph. I dont know how useful/realistic it will portray it but it might help with visualizing the problem and debugging.

## Data

This folder contains input files describing shunting yard layouts (yard_jsons folder) and scenarios (train_jsons folder) that I used for my research. They can serve as examples for creating your own, or can be used to generate problem instances for your own experiments.
